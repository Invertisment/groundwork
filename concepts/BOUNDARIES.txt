BOUNDARIES (package/module cuts)

CROSS-CUTTING NOTE:
- This concept doesn't name another layer — it's about where the seams
  go *within and between* the four layers (FUNCTIONAL_CORE, DATA,
  INFRA_LAYER, GLUE). Each of those layers still
  needs to be cut into modules/packages, and this file is about how.

PROPERTY TEST:
- A boundary is right if it contains everything needed to keep one
  business invariant true (e.g. "balance can never go negative" lives
  entirely inside one package, because that check can't be split
  without risking a race).
- A boundary is wrong — empirically, mechanically checkable — if
  implementing something inside it requires reaching into another
  package's internals, needing data it doesn't own, or creating a
  circular import.

WHY:
- This is the one part of the whole design that requires actual domain
  knowledge and cannot be discovered purely empirically by an agent.
  Deciding what the business genuinely treats as one atomic unit is a
  human judgment call — same idea as a DDD "aggregate."
- Everything else in this design (splitting a unit that's too big,
  detecting a leaking boundary) can be checked after the fact by
  tooling; the first cut cannot.

HOW IT'S ENFORCED (mechanical, once drawn):
- An allow list per layer: the layers its files may import. Anything
  not listed fails, so a layer added later starts with nothing allowed
  until its row is written.
    core:  core
    data:  core, data
    infra: core, infra
    glue:  every layer
  The rows hold across components: `a/core` may import `b/core`, never
  `b/infra`.
- Purity, for core and data: an allow list of the libraries they may
  import, the standard library's pure packages and each pure library
  (see REUSE.txt LIBRARIES IN THE LAYERS), so adding one is a diff
  someone reviews. A ban list (DB drivers, HTTP clients, filesystem,
  clock, random, framework types) only catches what someone thought to
  ban.
- Circular-import detection.
- The allow lists check direction, not placement: logic in the wrong
  layer passes as long as its imports are allowed. Placement stays
  with review (see INFRA_LAYER.txt KEEP IT THIN, GLUE.txt
  PROPORTIONALITY).
- These are plain CI checks (e.g. an import-linter / dependency-graph
  tool for whatever language the project uses) — the concrete tool
  is a per-project verification predicate, not defined in this file.

LAYER SHOULD BE THE BOTTOM-LEVEL CUT:
- Keep the upper package structure normal for the language/ecosystem —
  components/features as the project would naturally package them
  (`payments/`, `notifications/`, `camera/`, nested as deep as needed).
  The layer is the innermost directory that holds source files:
  `src/payments/ledger/core/`, `src/payments/ledger/infra/`,
  `src/payments/ledger/glue/` (plus `data/` where that layer
  exists).
- Not layer-first (`src/core/payments/`, `src/infra/payments/`): that
  scatters one component — and the business invariant it protects —
  across several distant trees, working against the invariant-based
  cut above. Bottom-level layers keep a component's core, infra and
  glue next to each other while still making each file's layer
  explicit.
- Not a flat layout with no layer directories at all: a linter has no
  way to know which layer a file belongs to unless that's encoded in
  the path itself.
- The allow list stays generic by matching the layer segment of the
  path rather than a fixed prefix: "files under `**/core/**` import
  only from `**/core/**`" covers every component added later, with no
  update to the check itself.
- Required companion checks, since the path is now the only thing
  declaring a file's layer:
  - Every source file sits under exactly one layer directory; a source
    file outside any layer directory fails CI.
  - Layer directory names are reserved — no nesting one layer inside
    another (`core/infra/`), and no component may reuse a layer name
    for something else.
- This makes the lint more involved than a single prefix rule. That's
  an accepted cost: it's still a mechanical predicate, and generating
  it per project (in whatever import-linter/dependency-graph tool the
  language has) is exactly the kind of check an agent can write and a
  human can verify once.

ADDING A LAYER:
- A new layer is justified only by an import-direction rule it adds
  that catches a real mistake (DATA's "core can't import the real
  tables" catches logic and tests bound to one table). A grouping that
  changes no rule — say, shapes split out of core, importable by
  everyone exactly like core already is — is a component or a file,
  not a layer.
- Each layer costs a reserved directory name and a row in every
  project's checker, so the bar is the rule it adds, not how tidy the
  grouping looks.

HUMAN-GATED, NOT AUTOMATABLE:
- Drawing the first boundary. An agent can tell you a boundary is
  *leaking* (mechanical signal), but not what the boundary *should
  have been* — that requires knowing the invariant.
- Treat a repeated boundary violation as a prompt to re-examine
  whether the invariant was mis-identified, not just a bug to silence.
