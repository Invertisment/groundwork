BOUNDARIES (package/module cuts)

CROSS-CUTTING NOTE:
- This concept doesn't name a fifth layer — it's about where the seams
  go *within and between* the four layers (FUNCTIONAL_CORE,
  INFRA_LAYER, SAGA_COMPOSITION, GLUE). Each of those layers still
  needs to be cut into modules/packages, and this file is about how.

PROPERTY TEST:
- A boundary is right if it contains everything needed to keep one
  business invariant true (e.g. "balance can never go negative" lives
  entirely inside one package, because that check can't be split
  without risking a race).
- A boundary is wrong — empirically, mechanically checkable — if
  implementing something inside it requires reaching into another
  package's internals, needing data it doesn't own, or creating a
  circular import.

WHY:
- This is the one part of the whole design that requires actual domain
  knowledge and cannot be discovered purely empirically by an agent.
  Deciding what the business genuinely treats as one atomic unit is a
  human judgment call — same idea as a DDD "aggregate."
- Everything else in this design (splitting a unit that's too big,
  detecting a leaking boundary) can be checked after the fact by
  tooling; the first cut cannot.

HOW IT'S ENFORCED (mechanical, once drawn):
- Dependency-direction / import-direction checks: core cannot import
  infra or saga packages; infra cannot import saga internals;
  glue can import everything.
- Purity checks on the core: ban imports of DB drivers, HTTP clients,
  filesystem, clock, random, and framework types from core packages.
- Circular-import detection.
- These are plain CI checks (e.g. an import-linter / dependency-graph
  tool for whatever language the project uses) — the concrete tool
  is a per-project verification predicate, not defined in this file.

LAYER SHOULD BE THE TOP-LEVEL CUT:
- Make the layer itself the outer package/directory (`core/`, `infra/`,
  `glue/`), with feature packages nested inside each — not a flat
  layout of feature packages as siblings (`payments/`, `notifications/`,
  `camera/`) that merely happen to informally belong to one layer or
  another in a contributor's head.
- This is what keeps the import-direction check above generic instead
  of a growing list of hardcoded per-package rules: "nothing under
  core/* imports from infra/* or glue/*" automatically covers every
  package added later, under any layer, with no update to the check
  itself. A flat layout can't be checked this way — a linter has no
  way to know which feature package belongs to which layer unless
  that's encoded in the path itself.

HUMAN-GATED, NOT AUTOMATABLE:
- Drawing the first boundary. An agent can tell you a boundary is
  *leaking* (mechanical signal), but not what the boundary *should
  have been* — that requires knowing the invariant.
- Treat a repeated boundary violation as a prompt to re-examine
  whether the invariant was mis-identified, not just a bug to silence.
