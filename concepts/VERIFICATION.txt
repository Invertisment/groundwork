VERIFICATION (which kind of check to put a requirement behind)

CROSS-CUTTING NOTE:
- This is not a layer. It ranks the kinds of checks the other files
  rely on (types, import/purity rules, property tests, example tests,
  review) so each requirement gets put behind the strongest check
  that can actually express it.

WHY:
- An agent produces code faster than a human can read it, and its own
  claims about that code ("the core stays pure") are not evidence.
  Every requirement moved from review into a mechanical check is one
  nobody has to re-verify by eye on every diff.
- Mechanical checks also feed back inside the agent loop: a specific,
  deterministic failure is the most actionable signal an agent gets,
  and it doesn't dilute as context grows the way a prompt rule does.

STRENGTH (strongest -> weakest):
- "Strength" means how reliably a passing check implies the property
  holds — not how many kinds of bug it can see. Review sees the most
  kinds and guarantees the least.
1. Types that make illegal states unrepresentable. Wrong code doesn't
   compile; holds for every value on every path, not for sampled
   inputs. Limit: only invariants the type system can express.
2. Import-direction and purity rules (see BOUNDARIES.txt). Every file,
   every change. Structural only: proves the core can't do I/O, says
   nothing about whether it computes the right thing.
3. Property tests. Behavior over a generated distribution of inputs;
   can't be passed by special-casing examples (see DECOMPOSITION.txt).
   Limit: sampled, not proven, and only as good as the property — a
   too-loose property passes wrong code.
4. Example tests. Behavior at the specific points shown; an
   implementer that can see them can special-case each one.
5. Review. The only check of meaning and spec faithfulness, but not
   repeatable, drifts with attention, and doesn't scale with agent
   output.

VALUE FOR EFFORT — HUMAN (best -> worst):
- Effort here is human attention: reading a check closely enough to
  trust it's honest, once or on every change. An agent writes all of
  these; the human only has to read them.
1. Import/purity rules. A few lines of config read once, then they
   guard every file and every component added later.
2. Types. A type definition is short to read and holds on every path.
   Reading it well needs domain knowledge, the same kind the first
   boundary cut does (see BOUNDARIES.txt).
3. Property tests. Short, but the highest-stakes read: a too-loose
   property or a generator that misses valid inputs gives false
   confidence at scale. Worth the attention because this is where a
   human read can't be replaced.
4. Example tests. Each is easy to read, but there are many and each
   covers one point, so knowing what's covered means reading them all.
5. Review. All of the effort, again on every diff, growing with agent
   output.

VALUE FOR EFFORT — MACHINE (best -> worst):
- Effort here is what an agent spends writing the check and getting it
  to pass; value is how good the check is as feedback inside its loop
  — fast, deterministic, pointing at the exact cause — and how much a
  pass can be trusted.
1. Import/purity rules. Generated once from BOUNDARIES.txt; failures
   are instant and name the offending import.
2. Types. Compiler errors are the fastest, most precise feedback an
   agent gets. The cost is modeling the domain up front, and the
   temptation to cast past an error instead of fixing it.
3. Property tests. Finding the invariant is the hard part; once found,
   a shrunk counterexample is precise feedback. Pin the seed and keep
   failing cases as examples so a rerun is reproducible.
4. Example tests. Trivial to write, precise failures — but they invite
   special-casing (see DECOMPOSITION.txt), so the green they produce
   is worth the least of any test.
5. Review (an LLM reviewing LLM code). Cheap to run, but not evidence:
   correlated blind spots, nondeterministic, nothing to fail CI on.

TYPE TIER AVAILABILITY:
- In languages without a static type layer (plain JS, Python without a
  type checker, Clojure) tier 1 doesn't exist. The nearest substitute
  is a runtime schema/spec, which checks like a property test, not
  like a type.

READING THE LISTS TOGETHER:
- Weighed against value, effort barely reorders anything: both value
  lists end up close to the strength list. Strong checks are worth
  what they cost.
- The one consistent swap is import/purity rules above types: nearly
  as strong, far cheaper for both human and machine. That's why every
  project generated from this guideline gets them, not just the ones
  that find time.
- The lists diverge at the bottom: review costs the human everything,
  and gives the machine nothing worth trusting. Example tests are
  cheap for the machine but expensive for a human to read for
  coverage.
- Human attention is the binding constraint, not agent effort. Put
  each requirement as high on the strength list as the language and
  the requirement allow, and drop a tier only when the higher one
  can't express it — never because the higher one is more work for the
  agent.
- Review stays as the catch-all for what no mechanical check can
  express, above all whether the spec matches the actual requirement
  (human-gated, see DECOMPOSITION.txt TEST-SPEC INTEGRITY).

CHECKING THE CHECKS (mutation):
- A green suite says the code passes the tests; it doesn't say the
  tests would fail on wrong code. A too-loose property, or a generator
  that never reaches the interesting inputs, looks exactly like a
  strong one while it's green — and tiers 3 and 4 above are only as
  strong as that.
- Mutation testing measures it mechanically: change the code under
  test on purpose (flip a condition, drop a guard, pick the first
  match instead of the last, return the input unchanged) and run the
  tests. A mutant that survives is a rule nothing checks: tighten the
  property, widen the generator, or add an example for it.
- Most valuable when the same agent wrote the tests and the code (see
  DECOMPOSITION.txt TEST-SPEC INTEGRITY): correlated blind spots show
  up as surviving mutants, never as failing tests.
- Where the mutants come from matters as much as running them: a
  mutant only checks a rule someone (or something) thought to mutate.

MUTANT SOURCES (strongest -> weakest):
- "Strength" here is who picks the mutants. The fewer choices the
  author of the tests makes, the less their blind spots decide what
  gets checked.
1. A mutation tool for the language (e.g. Stryker for JS/TS, PIT for
   the JVM, mutmut for Python, cargo-mutants for Rust). Every operator
   on every line it covers; nobody picks.
2. A small generated mutator, where no tool fits the language or the
   build. A script applies a fixed set of operators to every place
   they match in core and saga files: flip a comparison (< to <=, ==
   to ~=), swap and/or, drop a not, add or subtract one from a number
   or an index, return the input or an empty value instead. Nobody
   picks here either; it's tier 1 with fewer operators. It's part of
   the harness, so a human reads it (AGENTS.md: never fully vibe the
   test harness).
3. Hand-placed markers: a named mutant written next to the line it
   changes (e.g. `-- @mutant id: from => to`). Only for mutants no
   operator produces, the ones that change meaning: the first match
   instead of the last, a scan run in the other direction, a guard
   dropped, a domain rule off by one in a way no operator spells.
- Markers supplement tier 1 or 2; they're never the only mutation
  gate past a first run. Write them from the requirement, not from the
  tests: by a human, or before the tests exist, or reviewed by a human
  with the requirement in hand. When the agent that wrote the tests
  also places the markers, a rule it never thought of gets neither a
  test nor a marker, and the run stays green.
- A project with markers only (no tool, no generated mutator) records
  that as a known gap in its GROUNDWORK.md.

EQUIVALENT MUTANTS:
- Some generated mutants can't change behavior (`>=` instead of `>`
  where the two sides are never equal). Each one goes on a list with a
  one-line reason. The list is counted like suppressions (see ESCAPE
  HATCHES): not dropped from the run silently, and not "killed" by a
  test pinned to implementation details.

MUTATION COST:
- A run repeats the suite once per mutant, so aim it at code with real
  logic (core, saga), not glue. Generated mutants can be limited to
  the lines a change touched, which keeps a per-change run cheap; the
  full run can be less frequent (nightly, before a release).
- A rising survival rate is the signal to read, like a rising
  suppression count below.

ESCAPE HATCHES:
- Every tier has a cheap bypass, and an agent blocked by a check takes
  the cheapest way past it:
  - types: `any`, unchecked casts, `unsafe`, `@ts-ignore`,
    `# type: ignore`.
  - import/purity/lint rules: suppression comments (`# noqa`,
    `eslint-disable`), or moving code to a path the rule doesn't scan
    (closed by BOUNDARIES.txt's "every source file sits under exactly
    one layer directory").
  - tests: skipping or deleting a test, loosening a property, editing
    the expected value instead of the code.
- A check is only as strong as its least-guarded bypass. Guard them
  mechanically:
  - Ban suppressions in CI, or allow them only with an inline reason
    and count them, so a rising count is visible.
  - Flag changes that touch a test and the code under test together,
    so the test diff gets read on its own rather than as part of the
    fix.
  - A loosened property or a narrowed generator shows up as surviving
    mutants (see CHECKING THE CHECKS above), even when the diff that
    loosened it looked harmless.
- Same order as everywhere else in this guideline: the mechanical
  signal finds the bypass, judgment decides whether it was legitimate.
