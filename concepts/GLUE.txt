GLUE (main / wiring)

PROPERTY TEST:
- Makes no business decisions. Only assembles/wires the other layers
  together: DI, routing, config loading, framework entry points.

WHY:
- This layer is safe to leave lightly tested — but only as long as it
  stays genuinely dumb. The moment it grows a branch on domain state,
  it has quietly become saga or core logic wearing glue's name, and
  needs to be tested and reasoned about as such.

BELONGS HERE:
- Dependency injection wiring — with a framework (Spring autowiring,
  Dagger/Hilt, etc.) or by hand. Neither is required by the other
  layers; see COMPOSITION ROOT below.
- Routing / request dispatch.
- Config and environment loading, and binding static data from the
  data layer (see DATA.txt) to the code that takes it as a parameter.
- Framework-mandated entry points: main(), an HTTP server bootstrap,
  an Android Activity/Service/InputMethodService registration.

COMPOSITION ROOT (DI without a framework):
- "Core/saga never imports infra" does not require a DI framework —
  it requires that only one place in the codebase ever references both
  a contract and its concrete implementation together, and that place
  is glue. Without Spring/Dagger/etc., that means constructing the
  concrete infra by hand in main and passing it into whatever core/
  saga code needs it (e.g. via constructor), instead of autowiring —
  same rule, same guarantee, no framework required.
- The principle underneath is dependency inversion (the D in SOLID):
  the contract is declared by the side that needs it, in its own terms
  (core or saga), and infra implements it. The import points from infra
  to the contract, against the direction of the call, so the
  import-direction check holds (see BOUNDARIES.txt). Glue is the one
  place that sees both sides and connects them.
- Core may declare a contract but never calls one (see
  FUNCTIONAL_CORE.txt EDGE CASES). Glue or saga calls it, hands core
  the result as plain data, and carries out the plain value core
  returns.
- This is a named pattern (Mark Seemann's "composition root"): the one
  place in the app where every concrete type gets instantiated and
  handed to the abstraction that needs it. A DI framework automates
  this; doing it by hand in main is the same pattern made explicit,
  not a workaround or a lesser version of it.

MULTIPLE INSTANCES ALLOWED:
- A platform may hand you several mandated entry points instead of one
  main() — e.g. Android's InputMethodService plus a share-target
  Activity. Each one stays glue as long as none of them decide
  anything; if one starts branching on domain state, that logic
  belongs in the saga or core layer instead, called from the entry
  point, not inlined into it.

DOES NOT BELONG HERE:
- Any conditional that depends on domain/business state.
- Any compensation, or any retry/ordering decision across
  independently-owned resources (that's saga layer).
- Exception: where the saga layer collapses away (see "MAY NOT EXIST"
  in SAGA_COMPOSITION.txt), plain retry/ordering of calls may sit here
  instead of in infra — as long as it doesn't branch on domain state.
  Once it does, or once a second resource joins the operation, it has
  outgrown glue.
- Any calculation or derivation (that's core layer).

PROPORTIONALITY (not literally zero conditionals):
- "No business decisions" doesn't mean zero conditionals of any kind.
  A single boolean wired straight to one UI affordance — a popup is
  open or closed, a button's label reflects which — is still glue,
  even though it's technically an if/else.
- The line is domain/business state versus presentation state local to
  the entry point itself. "Is this popup currently open" is
  presentation state; "does this user have permission to do X" or "is
  this order past its cancellation window" is a decision, even if it's
  a single line to check.
- Signal it's crossed the line: the conditional would need testing
  independent of the framework/UI to trust it, or it depends on data
  the entry point had to go fetch/decide rather than just its own
  current display state.

UI STATE WITH A RULE ACROSS FIELDS (transitions in core):
- A UI framework keeps state in its own containers (React hooks,
  Compose state, an Android ViewModel's StateFlow), so that state is
  held by glue. What changes it doesn't have to be.
- Trigger: the state has a rule spanning several fields — e.g. free
  seats plus assigned seats must add up to the venue's capacity, so
  assigning one moves it from one field to another. A single field
  wired to one affordance (see PROPORTIONALITY) stays plain glue, and
  so does presentation-only state (paging, an open popup, a scroll
  position).
- Once triggered: the state is a plain immutable value, and every
  change to it is a pure function in core, (state, input) -> newState
  (see FUNCTIONAL_CORE.txt). Glue holds the current value in the
  framework's container and replaces it with what a transition
  returns; each handler calls one transition and branches on nothing.
- Why this shape: "no business decisions" has no mechanical check, so
  logic in glue survives on review alone and grows there untested
  (event handlers are the path of least resistance in most UI
  frameworks). "Each handler calls one transition" is checkable at a
  glance, and the logic it moves out becomes reachable by property
  tests.
- A transition that doesn't apply to the current state (an id that's
  gone, a value out of range, an option that no longer exists) doesn't
  throw: it returns the state unchanged together with why, as a value
  — [state, rejection], a Result/Either, a sealed outcome type. The
  rejection is a closed set of reasons, not a message string.
  - Glue can then react (show a notice, shake a field), and mapping a
    reason to text is presentation, so it stays glue. Glue still
    doesn't decide whether the change was allowed; it only reports the
    answer core gave.
  - Not throwing matters because UI input races with state changes,
    and it keeps the invariants holding for any sequence of
    transitions — which is what the tests generate. It also gives
    them one more cheap property: a rejected transition returns
    exactly the state it was given.
- Cost: more indirection than an inline handler, and one state type
  can grow to know everything. Split it along invariants (see
  BOUNDARIES.txt), never by size.

TRANSITIONS ARE NOT THE SAME THING AS "REDUCER":
- The property is "pure function in core, the only way the state
  changes". How the set of transitions is spelled is per language and
  framework:
  - Plain functions or methods on an immutable value:
    `state.assign(seat, guest)` returning a new state (a Kotlin data
    class with `copy`, a Java record, a Go struct passed by value). No
    event type at all; this is enough.
  - A closed set of inputs plus one function over it: a sealed
    interface of event cases and an exhaustive `when` (Kotlin; Android
    MVI), sealed interfaces with records and a `switch` (Java 17+), a
    tagged union and a `switch` (TypeScript; Redux or React's
    useReducer), a custom type and `update` (Elm), re-frame events
    (Clojure). A plain enum works only while no case carries data —
    "assign this seat" does, so it needs sealed cases, not enum
    constants.
- What the closed set buys: the compiler checks every case is handled
  (exhaustive `when`/`switch`), and the transitions become data a
  generator can draw from and a log or a test can replay. Worth it
  once there are more than a few transitions; not required by the
  property.
- Where the platform can drop the state (Android process death, a page
  reload), a plain immutable value is also what's easiest to save and
  restore — the saving itself is infra (see INFRA_LAYER.txt EDGE
  CASES).

COMMENTS:
- One sentence where the wiring looks odd because of the platform: a
  lifecycle order, a framework quirk, a workaround. E.g. "collect
  garbage now: Lua shares the radio's heap".
- Wiring that needs more than a sentence to explain is usually
  deciding something: move the decision to core rather than going
  over the limit. Otherwise the limit is a budget, with a marker to go
  over it (see HUMAN_READING.txt CHECKS).

TESTING:
- Smoke-level only: does the app start and wire correctly.
- Wanting a real logic test here is a signal the code doesn't belong
  in this layer — move it, don't just add the test. For UI state, the
  usual destination is a transition in core (see above).
- Generative/property-based testing deliberately does not apply here:
  there's no logic to generalize over. Wanting one is the same signal
  as above — the code has stopped being glue.
