GLUE (main / wiring)

PROPERTY TEST:
- Makes no business decisions. Only assembles/wires the other layers
  together: DI, routing, config loading, framework entry points.

WHY:
- This layer is safe to leave lightly tested — but only as long as it
  stays genuinely dumb. The moment it grows a branch on domain state,
  it has quietly become saga or core logic wearing glue's name, and
  needs to be tested and reasoned about as such.

BELONGS HERE:
- Dependency injection wiring — with a framework (Spring autowiring,
  Dagger/Hilt, etc.) or by hand. Neither is required by the other
  layers; see COMPOSITION ROOT below.
- Routing / request dispatch.
- Config and environment loading.
- Framework-mandated entry points: main(), an HTTP server bootstrap,
  an Android Activity/Service/InputMethodService registration.

COMPOSITION ROOT (DI without a framework):
- "Core/saga never imports infra" does not require a DI framework —
  it requires that only one place in the codebase ever references both
  a contract and its concrete implementation together, and that place
  is glue. Without Spring/Dagger/etc., that means constructing the
  concrete infra by hand in main and passing it into whatever core/
  saga code needs it (e.g. via constructor), instead of autowiring —
  same rule, same guarantee, no framework required.
- This is a named pattern (Mark Seemann's "composition root"): the one
  place in the app where every concrete type gets instantiated and
  handed to the abstraction that needs it. A DI framework automates
  this; doing it by hand in main is the same pattern made explicit,
  not a workaround or a lesser version of it.

MULTIPLE INSTANCES ALLOWED:
- A platform may hand you several mandated entry points instead of one
  main() — e.g. Android's InputMethodService plus a share-target
  Activity. Each one stays glue as long as none of them decide
  anything; if one starts branching on domain state, that logic
  belongs in the saga or core layer instead, called from the entry
  point, not inlined into it.

DOES NOT BELONG HERE:
- Any conditional that depends on domain/business state.
- Any compensation, or any retry/ordering decision across
  independently-owned resources (that's saga layer).
- Exception: where the saga layer collapses away (see "MAY NOT EXIST"
  in SAGA_COMPOSITION.txt), plain retry/ordering of calls may sit here
  instead of in infra — as long as it doesn't branch on domain state.
  Once it does, or once a second resource joins the operation, it has
  outgrown glue.
- Any calculation or derivation (that's core layer).

PROPORTIONALITY (not literally zero conditionals):
- "No business decisions" doesn't mean zero conditionals of any kind.
  A single boolean wired straight to one UI affordance — a popup is
  open or closed, a button's label reflects which — is still glue,
  even though it's technically an if/else.
- The line is domain/business state versus presentation state local to
  the entry point itself. "Is this popup currently open" is
  presentation state; "does this user have permission to do X" or "is
  this order past its cancellation window" is a decision, even if it's
  a single line to check.
- Signal it's crossed the line: the conditional would need testing
  independent of the framework/UI to trust it, or it depends on data
  the entry point had to go fetch/decide rather than just its own
  current display state.

TESTING:
- Smoke-level only: does the app start and wire correctly.
- Wanting a real logic test here is a signal the code doesn't belong
  in this layer — move it, don't just add the test.
- Generative/property-based testing deliberately does not apply here:
  there's no logic to generalize over. Wanting one is the same signal
  as above — the code has stopped being glue.
