FUNCTIONAL CORE

PROPERTY TEST:
- Same input always produces the same output.
- No I/O, no mutation of anything outside its own return value.
- Fully testable with plain data in, plain data out — no mocks, no environment.

WHY:
- This is the part of the system that can be exhaustively unit-tested with
  nothing but fixture data. In a codebase too large or too fast-growing to
  read (see RAW_MESSAGES.txt), a green test suite over pure functions is
  the closest thing left to a trustworthy oracle.
- Converts "I need to read a huge amount of code to trust this" into
  "I need to trust this specific, small, deterministic function."

BELONGS HERE:
- Business rules and calculations (pay calculation, eligibility checks).
- Parsing and validation of already-fetched data.
- State-transition / reducer functions: reduce(state, event) -> newState.
- Saga deciders: the next step or compensation from a saga's recorded
  state (see SAGA_COMPOSITION.txt).
- Derivations/projections over a list of facts (e.g. coverageGaps(events, rules)).
- Pure UI-state-to-tree functions (e.g. a Compose composable that only reads
  from arguments passed in and returns a tree — no framework state reads).

DOES NOT BELONG HERE:
- Anything that reads the system clock, generates randomness, or reads
  environment/config directly instead of receiving it as a parameter.
- Anything that touches a DB, network, filesystem, camera, sensor, or
  any framework/OS API.
- Anything whose result depends on call order or prior calls (hidden state).

EDGE CASES:
- A "pure-looking" function that reads `now()` or the system timezone
  internally is not pure — pass time/timezone in as a parameter instead.
- UI rendering counts as core only if it is state -> tree with no reads of
  live OS/framework state inside the function body.
- A function that's pure but happens to be slow/expensive is still core;
  purity is about determinism and no I/O, not about performance.
- A function that imports a built-in data table (a product catalog,
  a rate table, a config constant) is pure, but it's bound to that one
  table: no test can give it any other input. Pass the data in as a
  parameter like any other config. The real table lives in the data
  layer and glue (the composition root) binds it (see DATA.txt). The
  same goes for types derived from the data (an id type built from the
  table's keys): logic typed by them only accepts the real data, so it
  takes plain ids instead and validates them against the table it was
  given. Adding an id to the data then never touches core.
- Core may declare a contract for infra to implement (dependency
  inversion, see GLUE.txt COMPOSITION ROOT), but doesn't call it. A
  core function that calls a port can only be tested against a fake,
  and the test then checks how the fake was used, not what was
  decided: at best a smoke test. Glue makes the call and
  passes core the result as plain data.

COMMENTS:
- None by default: a pure function is its signature, and its rules
  are its property tests (see HUMAN_READING.txt COMMENTS).
- At most one sentence on a function, and the check is hard: going
  over fails, and no marker gets past it. A function that needs more
  does more than one thing, so it goes to DECOMPOSE (see
  DECOMPOSITION.txt). Splitting core is cheap: pure functions compose
  with nothing to pass around but values.
- A project can relax this in GROUNDWORK.md, with a reason, for the
  whole project or a named module, never per function.
- Deleting the comment also gets past it, and no check can stop that.
  If the function reads fine without it, nothing was lost; if not,
  that's for review.

TESTING:
- Fast unit tests, plain data fixtures, no mocks, no test doubles needed.
- Prefer property-based/generative tests over enumerated examples
  wherever a requirement can be expressed as an invariant ("for all
  valid X, P(X) holds") rather than a fixed input/output list — pure
  functions are the easiest place in the whole system to do this,
  since they take plain data and need no hidden state set up per
  generated case. This is also the strongest defense against an
  implementer piling up special-cased branches instead of the general
  rule (see DECOMPOSITION.txt) — a hardcoded literal-keyed branch
  fails the moment the generator produces an input it wasn't written
  for.
- For state transitions (see GLUE.txt), generate sequences of
  transitions, not single inputs (model-based testing): apply each to
  the state the previous ones produced and assert the invariants after
  every step. Build each transition's input against the current state
  (an id that exists, now and then one that doesn't); inputs
  generated blind mostly don't apply, and the test passes without
  exercising anything. Round trips are cheap and strong: do-then-undo
  returns the starting state.
- Keep example-based tests alongside properties for concrete
  regression cases (a specific bug that was fixed, a documented edge
  case) — properties and examples are complementary, not either/or.
- Logic tests own their inputs: a small fixture written in the test, or
  a generated one. A test that loads shared data (the real catalog,
  config, seed data) fails one of two ways when that data changes:
  - with exact assertions, it breaks on every correct data edit — and
    one edit to a table many tests read breaks many tests at once, all
    for a change that was right;
  - with loose assertions, it silently changes what it checks: it
    still passes, but on other cases, and the coverage it lost shows
    up nowhere.
  Restating the data in the test is no fix either: it breaks the same
  way and gets updated by habit. Synthesized data makes the tests
  robust: they change only when the logic does.
- Real data is tested only in the data layer, and core can't import
  it, so a core test can't reach it (see DATA.txt TESTING).
