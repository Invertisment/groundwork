ADAPTER LAYER (mutable ops)

PROPERTY TEST:
- Touches something whose behavior you don't fully control at runtime:
  OS, network, DB, filesystem, clock, random, a hardware sensor, or a
  framework's async permission grant.

WHY:
- This layer looks boring but isn't — query construction, mapping,
  upsert semantics, pagination, scoping, permission state, retry
  behavior are exactly where subtle silent-wrong-data bugs live. They
  don't crash, they corrupt or leak data weeks later. This is the
  highest-risk layer to under-test, not the lowest.

BELONGS HERE:
- DB queries / CRUD operations.
- HTTP / external API calls.
- Camera, sensor, and other hardware access.
- Runtime permission requests (these are async and revocable — treat a
  denial the same as any other adapter failure mode, not a special case).
- Android intents, IME/InputConnection calls, share-sheet interactions.
- File I/O, system clock reads, random generation.

CONTRACT REQUIREMENT:
- Each adapter operation should declare (even informally, e.g. a comment
  or annotation) whether it's idempotent, what its failure modes are, and
  what — if anything — undoes it (a compensating action).
- This metadata is what the saga/composition layer consumes; without it,
  glue code has to go read adapter internals to know how to sequence
  things safely.

CONTRACT IS NOT THE SAME THING AS "INTERFACE":
- "Contract" here means a named, checkable seam separate from any one
  implementation. A language's `interface` keyword is one way to
  express that, not a requirement of the concept — the concrete
  mechanism differs enough across languages that it's worth choosing
  deliberately per project rather than assuming a Java shape:
  - Java/Kotlin: nominal typing — a class explicitly declares
    `implements`/`: Interface`, checked by the compiler.
  - Go: structural typing, no `implements` declaration at all — any
    type satisfies an interface implicitly just by having the right
    methods. Idiomatic Go leans on consumer-defined, minimal
    interfaces ("accept interfaces, return structs"), which fits the
    "core owns the port it needs" placement even more naturally than
    Java does.
  - Clojure: no static interface requirement. The nearest analog is a
    `protocol` (nominal, lighter-weight); it's also common to treat
    the contract as a function signature plus a `spec`/`malli` schema
    describing the data shape — the contract describes data, not a
    type. `clojure.spec` generators make this a natural fit for the
    generative testing this design already wants (see
    DECOMPOSITION.txt).
  - TypeScript: structural like Go, but erased at runtime — the
    contract is enforced at compile time only, not checkable in the
    running program.
  - Plain JS/Python without a type layer: no compile-time contract
    exists. The contract IS the shared test suite plus convention —
    which makes skipping that suite riskier here than in a typed
    language, since nothing else stands in for the contract at all.
- Whichever mechanism a project uses, the property that matters is the
  one at the top of this file (touches something you don't fully
  control) plus this one: the contract must be checkable independently
  of any single implementation, so a fake can be verified against it
  without also being the real thing.

TESTING:
- Contract tests against the real thing where feasible (a real test DB,
  an emulator/instrumented test for OS APIs) — not just a smoke test.
- If a fake of this adapter is used elsewhere (saga-layer tests), the
  same contract-test suite must be run against both the real adapter and
  the fake, to guarantee they never silently diverge. A fake that lies is
  the single biggest risk in this whole design — everything downstream
  stays green while the real thing breaks in production.

EDGE CASES:
- Android lifecycle-forced state loss (rotation, low-memory process
  kill) is an adapter concern, not a bug in your logic — anything not
  durably saved before the process can die is effectively at risk here.

GENERATIVE TESTING (where it applies here):
- Most adapter behavior is contract-tested against the real system, not
  a good fit for property-based generation. The exception is any
  adapter with a clean round-trip property — encode/decode, serialize/
  deserialize, parse/format (e.g. a QR encoder/decoder: for all valid
  text, decode(encode(text)) == text). Where that shape exists, a
  property test is a strong supplement to the real-system contract
  test, and for the same reason as elsewhere (see DECOMPOSITION.txt):
  it can't be satisfied by hardcoding a few literal cases.
